先记这几条

面试开口之前，把这四句话变成条件反射。它们决定你是「用过 Agent」还是「懂 Agent」。

1. 能不用 Agent 就不用。

Anthropic 的核心观点：大多数需求用一条固定流程（workflow）就够了。Agent 的代价是成本、延迟、不可预测性和调试难度。先问「这活儿的步骤是确定的吗」，确定就别上 Agent。

2. Agent = 模型 + 工具 + 循环 + 记忆。

四者缺一，它就退化成一条链式调用。判断一个系统是不是 Agent，看控制流由谁决定 —— 由模型在运行时决定，才叫 Agent。

3. 可靠性靠架构，不靠模型更聪明。

单步 95% 正确，20 步之后只剩 36%。所以要步数上限、检查点、可回滚、独立的验证环节、关键节点人审。

4. 上下文是稀缺资源。

能塞进窗口 ≠ 该塞进窗口。上下文越长，有效注意力越被稀释，成本和延迟同步上升。学会做减法，比学会做加法更值钱。

六层知识体系

从上往下是依赖关系：上层不牢，下面全是空中楼阁。

01

概念地基

能讲清边界
  • 三种形态：Chain（固定管道）→ Workflow（人写死的编排）→ Agent（模型决定控制流）。
  • 五种 Workflow 模式：prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer。
  • 什么时候不该用：步骤确定、延迟敏感、结果必须可复现、错误代价高 —— 这四种情况都不该用 Agent。
02

核心循环

能画出来
  • ReAct：Thought → Action → Observation 交替。边想边做，灵活，但容易跑偏、步数多。
  • Plan-and-Execute：先出完整计划再逐步执行。省 token、可并行，但计划错就全错，通常要配一个 replanner。
  • Reflexion：失败后自我复盘并重试，把「反思」写回上下文。适合有明显对错反馈的任务。
  • 搜索式规划：Tree of Thoughts / LATS，把推理当搜索，成本高，一般只用在难题上。
03

四大支柱

面试主战场
  • Planning：任务拆解、子目标管理、动态重规划。
  • Memory：工作记忆（上下文 message）、情节记忆（历史轨迹，向量库）、语义记忆（事实与偏好，结构化或知识图谱）。难点从来不是存，而是「写入什么、何时检索、怎么遗忘」。
  • Tool Use：函数调用、参数 schema、工具粒度与数量、错误可恢复性、写操作的幂等与确认。
  • Context Engineering：RAG 精准投喂、compaction 压缩摘要、子 Agent 隔离上下文、大文件放外部按需读取。
04

多智能体

会讲取舍
  • 常见形态：Supervisor（主管分发）、Hierarchical（分层）、Swarm（对等移交）、Debate（对抗验证）。
  • 通信协议：A2A、agent card、任务交接的上下文传递格式。
  • 真实代价：错误累积、通信开销翻倍、调试链被拉长、成本成倍上涨。只有任务能清晰分工、需要上下文隔离、或需要独立视角验证时才值得。
05

工程落地

区分实习生和工程师
  • 编排框架：LangGraph（状态图 + 检查点）、OpenAI Agents SDK、AutoGen、CrewAI。选型要能说清为什么，并且敢说「不依赖框架我也能写」。
  • 可观测性：trace / span 级别的记录，能回放一次完整任务；Langfuse、LangSmith、OpenTelemetry。
  • 人机协同：敏感操作前暂停等审批，中断可恢复，状态要能持久化。
  • 安全：工具权限最小化、沙箱执行、输出校验；预算与步数上限防跑飞。
  • 成本与延迟：模型路由、prompt 与结果缓存、并行工具调用、流式输出。
06

评估度量

最容易被问倒
  • 三个层次：单步（工具选对没、参数对没）、轨迹（步骤合理吗、有无冗余和绕路）、端到端（完成率、步数、成本、延迟）。
  • 三种手段：规则断言、LLM-as-judge、人工抽检。judge 也要校准，别把它当真理。
  • 工程习惯：建一个几十条的回归数据集，每次改 prompt 或换模型都跑一遍，看的是趋势不是单次分数。

12 道高频问题

红色是面试官在等的关键词。答不上后三条，基本会被判定为「只调过 API」。

01Agent 和 Workflow 的区别？什么时候不该用 Agent？
区别在控制流由谁决定：Workflow 是人提前写死的，Agent 是模型运行时决定下一步。不该用的场景：步骤确定、延迟敏感、结果必须可复现、错误代价高。
02ReAct 和 Plan-and-Execute 的区别？
ReAct 边想边做，每步依赖上一步观察，灵活但易跑偏、步数多；Plan-and-Execute 先规划后执行，省 token 且可并行，但计划一旦错就全错，通常要配 replanner 动态修正。
03Agent 的记忆怎么设计？
分三层：工作记忆（上下文里的 message）、情节记忆（历史任务轨迹，存向量库）、语义记忆（事实与偏好，结构化或知识图谱）。真正难的是写入什么、何时检索、怎么遗忘。
04上下文是越长越好吗？
不是。存在 context rot：长度上去后有效注意力被稀释，准确率下降，成本和延迟同步上升。策略是 RAG 精准检索、compaction 摘要压缩、子 Agent 隔离上下文、大文件外置按需读取。
05MCP 是什么？解决什么问题？
Model Context Protocol，把工具 / 资源 / 提示词的接入标准化为 client-server 结构，解决 M×N 的集成爆炸问题 —— 可以类比成「工具界的 USB-C」。
06工具该怎么设计才不出错？
数量克制（单轮 5–10 个以内效果最好）；工具名和描述是写给模型看的 API 文档；参数 schema 要严格；错误要可恢复，返回有意义的报错而不是抛异常；写操作必须幂等并加人工确认。
07多 Agent 一定比单 Agent 好吗？
不一定，多数情况更差。代价是错误累积、通信开销、调试困难、成本成倍。只有当任务能清晰分工、需要上下文隔离、或需要对抗性验证时才值得上。
08怎么评估一个 Agent？
三层：单步、轨迹、端到端（完成率 / 步数 / 成本 / 延迟）。手段是规则断言 + LLM-as-judge + 人工抽检。关键工程习惯是回归数据集：改一次 prompt 就跑一遍全量。
09Prompt Injection 怎么防？
根因是不可信输入和系统指令处在同一上下文里。纵深防御：工具权限最小化（只读优先）、敏感操作人工确认、沙箱执行、外部内容明确标记为「数据」而非「指令」、输入输出过滤。没有银弹，别承诺能根治。
10模型越来越强，为什么 Agent 还是不可靠？
误差累积：单步 95% 正确率，20 步后只剩约 36%。所以要在架构上补：步数上限、检查点与回滚、独立验证环节、关键节点人审。
11成本和延迟怎么优化？
模型路由（简单步骤走小模型）、prompt 缓存与结果缓存、并行工具调用、压缩上下文长度、限制步数、流式输出改善体感。
12你会选哪个框架？
先声明不依赖框架也能手写。需要状态机与持久化 → LangGraph；想要轻量 → OpenAI Agents SDK 或自研；多 Agent 研究 → AutoGen。选型维度：是否需要持久化状态、是否要 human-in-the-loop、团队熟悉度。

手写骨架

面试让你「实现一个 Agent」时，这段结构能覆盖 80% 的考点：循环、工具分发、上下文写回、终止条件、步数保护。

# 一个最小可用的 ReAct Agent —— 不依赖任何框架
def run_agent(goal, tools, max_steps=10):
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user",   "content": goal},
    ]

    for step in range(max_steps):          # 步数上限：防跑飞
        resp = llm.chat(messages, tools=tools)  # 模型自己决定：回答 or 调工具

        if not resp.tool_calls:              # 没有工具调用 → 任务结束，输出答案
            return resp.content

        messages.append(resp)                  # Thought + Action 写回上下文
        for call in resp.tool_calls:          # 支持一轮多个工具并行调用
            try:
                result = TOOL_REGISTRY[call.name](**call.args)
            except Exception as e:
                result = f"工具报错：{e}，请调整参数后重试"  # 错误要可恢复
            messages.append(tool_message(call.id, result))

    return "达到最大步数，任务未完成"

能接着往下讲这几点，就是加分项：工具出错如何让模型自愈、如何把长历史做压缩、如何在此处插入 human-in-the-loop 断点、如何给每一步打 trace。

常见失分点

这几句一说出口，面试官对你的评价就会掉一档。

别说这些话

  • 「多 Agent 比单 Agent 强」—— 不给出场景和代价，等于没想过成本。
  • 「上下文窗口大，全塞进去就行」—— 完全不懂 context rot 和注意力稀释。
  • 「用 RAG 就不会幻觉了」—— 检索错、引用错、拼装错，幻觉照样有。
  • 「框架会自动帮我搞定」—— 面试官在测你到底懂不懂框架下面发生了什么。
  • 只讲功能不讲评估 —— 没有评估体系的 Agent 项目，在生产上等于没交付。
  • 把 prompt engineering 当成全部 —— 现在更看重 context engineering 和系统架构。
